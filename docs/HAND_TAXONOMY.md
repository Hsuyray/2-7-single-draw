## 0. 規則依據

`docs/game_rules.md` 是空檔案 [確認],所以規則以 `solver/hand_evaluator.py` 為準:
- 牌小者勝;A 只當大牌(A-5-4-3-2 是 A 高，不是順子);順子、同花算壞牌。
- 最強是不同花的 7-5-4-3-2。
- 牌力只取決於點數和是否同花，所以兩套分類都只看這兩樣，組合數可以精確計算。

## 1. 兩套分類
- **predraw**:換牌前的起手牌。pat 牌依最高兩張分格;其他牌依「可以抽的牌型」分格。
- **postdraw**:換牌後的最終牌力。

每一手 5 張牌在每套分類中**恰好落在一格** [確認，測試涵蓋全部點數組合與同花與否]。

## 4. 和 solver 抽象的對應

### 4.1 postdraw:bucket 0 合併了 7-5 到 9-6 [確認，結構];影響 [推測]
`PostdrawStrengthBucket` 的 bucket 0 同時包含 7-5、7-6、8-5、8-6、8-7 和部分 9-6。換牌後下注時，最強的 7-5-4-3-2 和 9-6-x-x-x 用同一個策略。原因是 128 個 bucket 在每個類別內依出現頻率切分，強牌稀少，所以全擠在一起。

[推測] 這對 postdraw 的價值下注 / 跟注影響很大，屬於 **B3**(postdraw 策略品質)要量化的問題;D3 不改 bucket。產品顯示時，7-5 和 9-6 會顯示同樣的頻率，要在 UI 上說明。

### 4.2 predraw:`DrawHandBucket` 有 208 / 1,068 個跨兩格 [確認]
主要原因是 bucket 把 8 和 9 合在一起，而本分類用「≤ 8」決定保留的牌。range 顯示時每手牌仍查自己 bucket 的策略，一格的頻率是格內各手牌依組合數加權的平均，所以這只是解析度限制，不會算錯。

## 5. [待決] 需要你決定的事

1. **「換 3 張以上」占 55%**,對 range grid 太粗。要不要再分，例如依保留的 2 張最高牌(「留 2 張 ≤ 5」「留 2 張 ≤ 7」「什麼都不留」)?
2. **保留牌的上限是 8**(`DRAW_KEEP_MAX`)。9 開頭的 4 張(例如 9-7-3-2)目前算「換 2 張」。職業玩家會把「換 1 張到 9」當成一格嗎?
3. **pat 的上限是 T**(`PAT_TOP_MAX`)。T 高的牌多半會被拆，要不要歸到換牌手?
4. **「順 / 粗」的分界**:目前順 7 = 第二張 ≤ 5,粗 7 = 7-6;8 同理。符合你的習慣嗎?
5. **9 的分格**:9-6 或更好 / 9-7 / 9-8 三格，還是合成一格?
6. 要不要把 **順子聽牌的風險**(例如 3-4-5-6 兩頭都會成順)當成獨立的格?
